## BL-001 macOS での internal/routeproxy の自動テストが未実行

### 概要と問題点

- **現状の事象**: `internal/routeproxy` のテストは Linux と Windows で成功しているが、macOS では `go vet` だけで、テストを実行していない。macOS では端末の制御 (`tty_darwin.go` の `TIOCGETA`・`TIOCSETA`) と、Unix のパスワード ファイルの権限の確認を使う。
- **本来あるべき姿**: CI (ubuntu、windows、macos) でテストが成功する。

### 経緯と見送り理由

- **摘出契機**: 実施時。
- **今回の見送り理由**: CI は `main` へのプッシュと PR でしか動かない。ブランチ `feat/ssh-route-proxy` には PR を作っていない。
- **継続作業での経緯と対処**: `workflow_dispatch` で CI を実行し、macos-latest でテストが成功したため解消した (2026-11-13)。文書の検証済みの範囲も「検証済」にした。

### 影響範囲とリスク

- **影響対象**: macOS のクライアントで使う `host-shell connect`。
- **放置した場合のリスク**: macOS 固有の誤りが、利用者の環境で初めて見つかる。

### 推奨される対応策

- **恒久対応案**: PR を作るか `workflow_dispatch` で CI を起動し、macOS のジョブの結果を確かめる。成功したら `docs/ja/ssh-proxy.md` と英訳の検証済みの範囲を「検証済」にする。
- **参考情報**: `.github/workflows/ci.yml`

## BL-002 Windows のコンソール ウィンドウでのパスワードの手入力を確かめていない

### 概要と問題点

- **現状の事象**: Windows で端末からパスワードを入力したときに入力が表示されないことは、疑似コンソール (ConPTY) から 1 文字ずつ送って確かめた。人がコンソール ウィンドウ (Windows Terminal、conhost) で手入力する方法では確かめていない。
- **本来あるべき姿**: 手入力でも入力が表示されず、接続できる。

### 経緯と見送り理由

- **摘出契機**: Windows の実機での検証時。
- **今回の見送り理由**: 検証はエージェントが行ったため、手入力の操作ができなかった。
- **継続作業での経緯と対処**: ユーザーが Windows Terminal と conhost で手入力して確認した。その際に見つかった Ctrl+C で中断したときの後始末の不具合と空行を修正し (コミット b7b7516)、再確認して解消した (2026-11-13)。

### 影響範囲とリスク

- **影響対象**: `internal/routeproxy/tty_windows.go`。MCP の構成 (端末なし) には影響しない。
- **放置した場合のリスク**: 低い。ConPTY でも同じコンソールの入力モードの切り替えを通っている。

### 推奨される対応策

- **恒久対応案**: 利用者が Windows Terminal で `ssh` を直接実行し、パスワードの入力欄で入力が表示されないことを確かめる。
- **参考情報**: 検証記録の「Windows の実機 (結果)」の 5e

## BL-003 SOCKS・TELNET 形式のプロキシに対応していない

### 概要と問題点

- **現状の事象**: `host-shell connect` は HTTP `CONNECT` だけに対応し、`-S`・`-s`・`-T`・`-t`・`-c` などはエラーになる。Tera Term と connect.c は SOCKS4/5 と TELNET 形式にも対応している。
- **本来あるべき姿**: 利用者の環境で SOCKS が使われている場合に、同じ互換の範囲で使える。

### 経緯と見送り理由

- **摘出契機**: 前提検討時 (Q-001)。
- **今回の見送り理由**: 要求の対象が HTTP CONNECT の Basic 認証であるため。
- **継続作業での経緯と対処**: ユーザーの判断により、対処不要としてクローズした (2026-11-13)。

### 影響範囲とリスク

- **影響対象**: SOCKS プロキシを使う環境の利用者。
- **放置した場合のリスク**: 該当環境では OpenSSH の他の手段 (`nc -X 5` など) が必要になる。

### 推奨される対応策

- **恒久対応案**: 要望が出た時点で、SOCKS5 (ユーザー名・パスワード認証) から追加する。検証には SOCKS サーバーのコンテナーを用意する。
- **参考情報**: connect.c の `-S`、`SOCKS5_USER`、`SOCKS5_PASSWD`

## BL-004 Basic 以外のプロキシ認証 (NTLM、Negotiate、Digest) に対応していない

### 概要と問題点

- **現状の事象**: 企業のプロキシには NTLM や Negotiate (Kerberos) を要求するものがある。`host-shell connect` とインターネット向けプロキシ (`bridge`) のどちらも Basic だけに対応する。
- **本来あるべき姿**: Windows の統合認証のプロキシでも、追加の中継なしで接続できる。

### 経緯と見送り理由

- **摘出契機**: 前提検討時 (Q-002)。
- **今回の見送り理由**: Go の標準ライブラリが対応しておらず、外部ライブラリと Windows の SSPI が必要なため。文書では、cntlm などのローカル中継を挟む方法に触れている (未検証)。
- **継続作業での経緯と対処**: ユーザーの判断により、対処不要としてクローズした (2026-11-13)。

### 影響範囲とリスク

- **影響対象**: NTLM・Kerberos のプロキシを使う環境。
- **放置した場合のリスク**: 利用者がローカル中継を自分で用意する必要がある。

### 推奨される対応策

- **恒久対応案**: まず cntlm などの迂回を検証して文書を「検証済」にする。需要があれば SSPI による Negotiate を設計する。
- **参考情報**: `docs/ja/ssh-proxy.md` の「制限」

### 経緯と見送り理由

- **摘出契機**: 前提検討時 (Q-007)。
- **今回の見送り理由**: 中継サーバーへの実行ファイルと資格情報の配置は、リスクと手順の両面で別の判断が必要なため。
- **継続作業での経緯と対処**: ユーザーの判断により、対処不要としてクローズした (2026-11-13)。

### 影響範囲とリスク

- **影響対象**: 中継サーバーの先にプロキシがある環境。
- **放置した場合のリスク**: その環境では host-shell に接続できない。

### 推奨される対応策

- **恒久対応案**: 中継サーバーへの `host-shell` の配置 (`deploy.sh` の応用) と、資格情報の置き場所・権限の方針を設計する。
- **参考情報**: Q-007

## BL-006 パスワードの入力手段が端末とファイル・環境変数に限られる

### 概要と問題点

- **現状の事象**: `SSH_ASKPASS` と OS の資格情報ストア (Windows 資格情報マネージャー、macOS キーチェーン、libsecret) に対応していない。パスワード ファイルは平文である。
- **本来あるべき姿**: 平文のファイルを置かずに、MCP の構成 (端末なし) でも資格情報を渡せる。

### 経緯と見送り理由

- **摘出契機**: 前提検討時 (Q-005)。
- **今回の見送り理由**: 3 つの OS それぞれの実装と検証が必要なため。
- **継続作業での経緯と対処**: ユーザーの判断により、対処不要としてクローズした (2026-11-13)。

### 影響範囲とリスク

- **影響対象**: パスワードの平文保存が許されない環境。
- **放置した場合のリスク**: 運用規程によっては利用できない。

### 推奨される対応策

- **恒久対応案**: Windows 資格情報マネージャーから読む `--credential-target` のようなオプションを検討する。
- **参考情報**: Q-005
