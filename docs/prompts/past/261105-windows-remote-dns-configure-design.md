# Windows の名前解決設定の自動化の設計 (2026-11-05)

> [!IMPORTANT]
> 作業時点の記録です。現在の仕様と検証済みの範囲は [接続元を使う名前解決 (remote-dns)](../../ja/remote-dns.md) の「Windows の接続先」を参照してください。前提の設計は [Windows 向け remote-dns の設計](261104-windows-remote-dns-design.md) にあります。

## 背景

Windows の接続先で OS の名前解決を host-shell の DNS サーバーへ向けるには、NRPT 規則と IPv4 のデフォルト ルートが必要である。前回の設計では、OS の設定は管理者が手で行い、host-shell は変更しないとしていた。検証ではデフォルト ルートを ActiveStore に追加しており、これは再起動で消える。一方、NRPT 規則はレジストリーに残る。設定が永続しない、または一部だけ残るのであれば、手作業ではなく自動化すべきという方針に変えた。

## 調べたこと

test-bed (前回と同じ Windows 11 Enterprise ビルド 26300 の閉じたネットワーク) で確認した。

| 確認 | 結果 |
|---|---|
| デフォルト ルートなし | `getaddrinfo` は WSANO_DATA |
| 次ホップがオンリンク (`0.0.0.0`、Ethernet) | 成功 |
| 次ホップが転送しないホスト (192.168.250.1)、メトリック 9999 | 成功 |
| 次ホップがループバック インターフェイス | 成功 |
| 上の 3 つのルートで外部 (1.1.1.1:443) へ | どれも届かない |
| 外部への直接接続の失敗までの時間 | ルートなし 84 ms (`unreachable network`)、ルートありはどれも約 21 秒でタイムアウト |
| 再起動後 | NRPT 規則 (`HKLM\SYSTEM\CurrentControlSet\Services\Dnscache\Parameters\DnsPolicyConfig`) は残り、ActiveStore のルートは消える |

次ホップは何でもよく、`getaddrinfo` は「IPv4 のデフォルト ルートがあるか」だけを見ていると判断した。単一ラベルの名前 (接続元のホスト名) は、ルートの有無にかかわらず解決できなかった。Windows が単一ラベルの名前を DNS に送らないためと考えられるが、確かめていない。

## 判断

- 接続先のオプション `--remote-dns-configure` を追加し、利用者が明示的に選んだ場合だけ host-shell が OS の設定を変える。既定の動作 (OS の設定を変えない) は維持する。
- 規則は OS 側で揮発するものではなく、起動時の追加 (注入) と終了時の削除 (除去) を一組で行う操作と位置づける。異常終了では規則が残るため、スキルと文書に、指定前に利用者の承諾を得ることを明記した。
- デフォルト ゲートウェイがある接続先では、ルートは追加せず NRPT 規則だけを追加する。
- ルートはループバック インターフェイスを次ホップにする。どのネットワーク アダプターにも依存せず、LAN に ARP を出さない。オンリンクやゲートウェイを次ホップにした場合と比べて、失敗までの時間は変わらない。
- ルートは ActiveStore に入れる。異常終了しても再起動で消える。既存のデフォルト ルートがあれば追加しない。
- NRPT 規則には永続しない領域がない。そのため、コメントに `host-shell-remote-dns pid=<プロセス ID>` を付け、次の起動時に、動いていないプロセスの規則を片付ける。手動手順のコメント `host-shell-remote-dns` だけの規則も片付けの対象にする。メトリック 9999 のループバックのデフォルト ルートは、host-shell が追加したものとみなして片付ける。
- 動いている別の host-shell (プロセス名が同じ) の規則があれば、起動時に停止する。同じ待ち受けアドレスの 2 つ目のセッションは、設定より先に bind エラーで停止する (DNS サーバーの待ち受けの後に設定を行う)。
- 昇格していないトークンでは、PowerShell を呼ぶ前に停止する (`IsElevated`)。
- 設定と削除は、Windows PowerShell 5.1 の NRPT・NetTCPIP コマンドレットを `-EncodedCommand` で呼んで行う。埋め込む値は、検証済みの IP アドレス、プロセス ID、実行ファイル名に限る。
- 終了時の削除は `Target.Close` の最初に行い、DNS サーバーを閉じる前に OS の設定を戻す。

## 検証

`e2e` の検証スクリプト (Python の JSON-RPC ハーネス) で、bridge 経由で次を確認した。

| 確認 | 結果 |
|---|---|
| 動いていない PID の規則、コメントだけの規則、ループバックのルートを置いて起動 | 3 つとも片付けてから、規則とルートを追加。`sys_get_info` の `remote_dns_configured` に変更が並ぶ |
| セッション中の名前解決 | .NET、Node.js `dns.lookup`、`curl.exe` (名前解決後に接続タイムアウト)、`ping` (名前解決後に応答なし) |
| 正常終了 | 規則とルートが消える |
| 接続先の host-shell を `Stop-Process -Force` で終了 | 規則とルートが残る。次の起動で片付けてから設定し、終了時に消える |
| 接続元の bridge と ssh を `taskkill /T /F` で終了 | 3 秒後には規則とルートが消えている (標準入力の終了で正常に後片付けが走る) |
| 既存のデフォルト ルート (192.168.250.1) がある | ルートを追加せず、終了後も既存のルートが残る |
| 自動テスト | `resolverAddress` (ポート 53 とループバックの検査)、Windows・Linux・macOS 向けの `go vet` |

## 残課題

- 昇格していないセッションでのエラーの確認
- IPv6 のみの環境 (AAAA の回答に IPv6 のデフォルト ルートが要るか)
- 単一ラベルの名前の扱い
- `nslookup` と NRPT 規則の関係、Windows Server と arm64 での確認
