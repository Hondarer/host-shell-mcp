## BL-001 Linux arm64 の接続先での実機確認

### 概要と問題点

- **現状の事象**: スキル `host-shell-code-server` は Linux arm64 (aarch64) の接続先を対象としていますが、確認したのは、配布アーカイブと既定の拡張機能 (linux-arm64 向け) の取得と SHA-256 の照合、および install が `uname -m` の `aarch64` で arm64 の配布物を選んで展開することまでです。arm64 の実機で code-server を起動し、拡張機能を導入し、ブラウザーから利用することは確認していません。
- **本来あるべき姿**: Linux x86_64 と同じく、取得、送付、導入、起動、転送、ログイン、既定の設定と拡張機能の反映が、arm64 の実機で確認されていること。

### 経緯と見送り理由

- **摘出契機**: 前提検討時に見送り (作業環境に arm64 の実機もエミュレーターもないため、取得・照合・選択の確認と未確認の記載にとどめる決定)。
- **今回の見送り理由**: arm64 の環境がなく、エミュレーターの導入には作業環境への管理者権限でのパッケージ追加が必要なため。

### 影響範囲とリスク

- **影響対象**: arm64 の Linux 接続先 (AWS Graviton、Raspberry Pi、Apple シリコン上の Linux VM など) での code-server の利用。
- **放置した場合のリスク**: arm64 版の code-server や、プラットフォーム別の拡張機能 (`ms-python.debugpy` の linux-arm64 版など) に固有の問題があっても、利用者が初めて使うときまで気付けません。

### 推奨される対応策

- **恒久対応案**: arm64 の Linux 環境 (実機、クラウドの arm64 インスタンス、または qemu-user-static を導入した x86_64 環境) で、`docs/ja/code-server.md` の手順を通しで確認し、文書の「確認状況」を更新します。
- **参考情報**: `.agents/skills/host-shell-code-server/scripts/linux/install.sh` (`linux_type`)、`docs/ja/code-server.md` の「対象」。

## BL-002 クライアント経由 HTTP プロキシでの、画面の拡張機能ビューからの導入の確認

### 概要と問題点

- **現状の事象**: クライアント経由 HTTP プロキシを有効にした接続先で、`install --extension <ID>` (code-server の CLI) により Open VSX から拡張機能を導入できることは確認しました。ブラウザーの拡張機能ビューから検索・導入する操作は確認していません。
- **本来あるべき姿**: 画面の拡張機能ビューからの検索と導入が、同じ許可先 (`open-vsx.org:443`、`openvsx.eclipsecontent.org:443`) で動くことが確認され、文書に記載されていること。

### 経緯と見送り理由

- **摘出契機**: 実装作業中の確認で、CLI の経路だけを確認したことによる。
- **今回の見送り理由**: 受入条件 (拡張機能の導入の確認) は CLI の経路で満たしており、画面の操作を自動で確認する手順を追加する必要があったため。

### 影響範囲とリスク

- **影響対象**: 閉鎖環境の code-server で、利用者が画面から拡張機能を探して導入する操作。
- **放置した場合のリスク**: 画面からの検索が別のホスト (画像やメタデータの配信元など) を必要とする場合、利用者が bridge の `proxy_status` で拒否先を調べて許可先を追加する必要があります。

### 推奨される対応策

- **恒久対応案**: HTTP プロキシを有効にした確認環境で、ブラウザーの拡張機能ビューから検索・導入し、bridge の `proxy_status` に現れる接続先を確認して、必要な `--proxy-allow-host` を文書に記載します。
- **参考情報**: `docs/ja/code-server.md` の「個別の拡張機能の導入」、`docs/ja/client-proxy.md`。
