### 現在の動作

- Windows で PowerShell (`powershell`、`pwsh`) が実行するコマンドの `stdin` は、既定でコンソールのコード ページに変換して渡します (`stdin_encoding` の既定が `system`)。
- コード ページで表せない文字 (英語の環境 (CP437) での日本語、日本語の環境 (CP932) での絵文字など) は、エラーになります。
- PowerShell は、標準入力 (`$input`) をコンソールの入力のコード ページで読み、スクリプトの中で `[Console]::InputEncoding` を変えても効きません。

### 事前検証の結果 (2026-10-31、セッション用の一時フォルダー)

この PC の Windows 11 (コンソールのコード ページ 932) で、`host-shell` と同じ起動の仕方 (コンソール ウィンドウなし、`-EncodedCommand`) で、UTF-8 の標準入力 `日本語 😀 Ελληνικά` を渡して `$input` をそのまま出力させました。

| 起動の仕方 | PowerShell 5.1 | PowerShell 7 | `[Console]::InputEncoding` | 所要時間 |
| --- | --- | --- | --- | --- |
| 直接起動 (現在) | 文字化け | 文字化け | 932 | 626 ms、835 ms |
| `cmd /d /s /c "chcp 65001 >nul & powershell ..."` | 正しく受け取れた | 正しく受け取れた | 65001 | 626 ms、954 ms |

Table: 事前検証の結果

あわせて、次のことが分かりました。

- cmd でコード ページを 65001 (UTF-8) にすると、同じコンソールを使う PowerShell が、標準入力を UTF-8 で読みます。絵文字など、どの文字も渡せます。
- コード ページを 65001 にすると、PowerShell 5.1 のメッセージが英語になりました (「モジュールを初めて使用するための準備しています。」が「Preparing modules for first use.」に)。日本語などの環境で、コンソールのコード ページが UI の言語を表せない場合に、Windows が英語のメッセージに切り替えるためです。
- 現在の起動の仕方でも、PowerShell 5.1 は、初回のモジュールの読み込みなどの進み具合を `#< CLIXML <Objs ...>` という XML で標準エラーに出力していました。エージェントには、意味のない文字列として `stderr` に見えます。

**Question**

PowerShell に、UTF-8 の標準入力を読ませる方式を、どれにしますか。

**Context**

- **経緯と背景**: PowerShell は、起動したときのコンソールの入力のコード ページで標準入力を読みます。スクリプトの中では変えられないため、PowerShell を起動する前に、コンソールのコード ページを 65001 (UTF-8) にする必要があります ([事前検証の結果](#事前検証の結果-2026-10-31セッション用の一時フォルダー))。

### Q-002 コード ページを変える場面

**Status**

**Question**

- **経緯と背景**: [Q-001](#q-001-powershell-に-utf-8-の標準入力を読ませる方式) の方式を、PowerShell を起動するすべての場面で使うか、標準入力を渡す場面だけで使うかの判断です。
- コード ページを 65001 にすると、標準入力のほかに、次の 2 つも変わります。

```text
案 A: 標準入力を渡す場面だけ
  exec_run {"command": "Get-Date"}                     → 今と同じ (直接起動)
  exec_run {"command": "$input | ...", "stdin": "日本語"} → cmd + chcp 65001 で起動
案 B: PowerShell を起動するすべての場面
  exec_run {"command": "Get-Date"}                     → cmd + chcp 65001 で起動
```

**Answer**

選択方式: 単一選択

- [ ] A: (推奨) 標準入力を渡す場面だけ (`stdin` を指定した場合と、`stdin_open` のジョブ)。
- [x] B: PowerShell を起動するすべての場面 (`pty` のジョブを除く)。

```text
案 A:   powershell.exe -NoProfile -NonInteractive -ExecutionPolicy Bypass -OutputFormat Text -Command
```

A の選択により、標準入出力がパイプなら、今のコンソールから離れて自分のコンソールを作ります。標準入出力がコンソールなら、コンソールに手を付けず、PowerShell の標準入力は今と同じ扱い (コンソールのコード ページに変換) にします。

回答の後に、コンソールの作り方を追加で検証しました (2026-10-31、この PC の Windows 11、セッション用の一時フォルダー)。

- **AllocConsole では、ウィンドウが開く**: この PC は、既定の端末が Windows Terminal (Windows 11 の既定) です。AllocConsole でコンソールを作ると、Windows Terminal のウィンドウが開き、表示されたままでした (`IsWindowVisible` が 1)。ウィンドウを隠す処理 (ShowWindow) は、Windows Terminal のウィンドウには効きません。SSH の接続先 (デスクトップのないセッション) では見えませんが、デスクトップのある環境 (この PC での確認、GitHub Actions など) では、ウィンドウが現れます。なお、版 1 と版 2 の事前検証でも、この PC にウィンドウが一瞬現れていたと考えられます。
- **ウィンドウのないコンソールに加わる方法では、ウィンドウが開かない**: `host-shell` が、ウィンドウなし (`CREATE_NO_WINDOW`) で補助のプロセス (`cmd.exe`、標準入力を閉じるまで待つ) を起動し、そのコンソールに加わり (AttachConsole)、補助のプロセスを終わらせます。この方法では、ウィンドウはなく (`GetConsoleWindow` が 0)、Windows Terminal も起動されませんでした。コード ページを 65001 にすると、PowerShell 5.1 と 7 は、UTF-8 の標準入力 (`日本語 😀 Ελληνικά`) を正しく受け取りました。準備にかかった時間は約 95 ms で、`host-shell` の 1 回の起動で 1 回だけです。

方針 (`host-shell` が自分のコンソールを持ち、PowerShell に使わせる) は変わらず、コンソールの作り方だけを、ウィンドウのないコンソールに加わる方法にします。最終仕様に、この作り方を書きます。

### Q-011 stdin_encoding に utf-8 を明示した場合

**Question**

PowerShell のコマンドで、`stdin_encoding` に `utf-8` を明示した場合は、どちらのコンソールで起動しますか。

**Context**

- **経緯と背景**: [Q-004](#q-004-powershell-の標準入力の既定の文字コード) の回答 A では、`stdin_encoding` を明示した場合は「その文字コードで渡し、コード ページは変えない」としています。この決まりどおりにすると、`utf-8` を明示した場合は、PowerShell を今と同じく自分のコンソール (コード ページ 932 など) で起動し、UTF-8 のバイトをそのまま渡すため、PowerShell 側で**文字化けします** (今の動作)。省略した場合 (既定の `utf-8`) は正しく受け取れるため、同じ `utf-8` でも、書いたかどうかで結果が変わります。
- 今の `host-shell` は、`stdin` を変換できないときのエラーで「`stdin_encoding` に `utf-8` などを指定する」よう案内しているため、`utf-8` を明示する使い方は、すでにありえます。

```text
stdin_encoding: "utf-8"           host-shell のコンソール    自分のコンソール (932)    → A: 正しく受け取る / B: 文字化け
stdin_encoding: "shift_jis" など  自分のコンソール           自分のコンソール          → コード ページに合わせて渡す
```

**Answer**
