## 調査結果

### 許可規則のポートの glob

接続先の `--allow-host` と bridge の `--forward-allow-local` は、どちらもポートを glob で照合します (`path.Match`)。たとえば `127.0.0.1:80??` は 8000〜8099 に一致します。範囲を指定する機能を追加しなくても、連続した 100 個または 10 個のポートは 1 つの規則で表せます。`docs/ja/reference.md` には `*:80` の例があります。

### code-server のポート 0

code-server 4.144.0 を `--bind-addr 127.0.0.1:0` で起動すると、OS が空きポートを割り当て、`HTTP server listening on http://127.0.0.1:35491/` のように実際のポートを出力しました (作業環境で、HOME を一時フォルダーに向けて確認)。スキルの手順は、この行を `job_read` の `until` で待っています。

### podman exec での接続

元案件の完了後に、作業環境の podman 4.9.4 (rootless) で、Oracle Linux 9 のイメージから作った使い捨てのコンテナーに接続しました。

- `podman exec -i <コンテナー> sh -c 'cat > …'` の標準入力から host-shell を配置し、SHA-256 の一致を確認しました。
- `host-shell bridge --forward-allow-local 127.0.0.1:8000 -- podman exec -i <コンテナー> /tmp/host-shell-0/host-shell --mcp --allow-forward-local` で、`sys_get_info`、`exec_run`、`transfer_push`、`job_start`、`forward_open` が動き、コンテナー内の `127.0.0.1:8000` の HTTP サーバーへ手元から接続できました。
- 接続を閉じた後、コンテナー内に host-shell とジョブのプロセスは残りませんでした。
- `podman exec` に `-t` を付けると、端末の制御で MCP のやり取りが壊れます。

### code-server と glibc

code-server の配布物に含まれる node (`lib/node`) は、glibc の動的リンカー (`/lib64/ld-linux-x86-64.so.2`) を使う実行形式です。musl を使う Alpine などのイメージでは、互換層を入れない限り動きません。host-shell 自身は静的リンクのため、Alpine でも動きます。

### 作業環境

- `docker` コマンドは podman の互換コマンドです (`docker --version` が `podman version 4.9.4-rhel` を返します)。本物の Docker Engine はありません。
- kubectl と Kubernetes のクラスターはありません。
- arm64 の実機はなく、qemu のエミュレーション (`binfmt_misc` の `qemu-aarch64`) も登録されていません。
- ローカルにある podman のイメージは Oracle Linux 8、9、10 の開発用イメージなどです。Alpine などの最小イメージはありません。
