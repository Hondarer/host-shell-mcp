# クライアント経由 HTTP プロキシ 最終仕様

検討 ID: 261031-client-proxy

版: 1

状態: 承認済み

## 1. 目的・構成

接続先プログラムが HTTP_PROXY/HTTPS_PROXY を使い、既存の SSH 標準入出力を経由してクライアント側 bridge のネットワークへアクセスできる機能を追加します。

    接続先アプリ
      → 127.0.0.1 の認証付き HTTP プロキシ
      → 既存 SSH stdio の JSON/Base64 チャネル
      → クライアント bridge
      → クライアントの上流プロキシ、または直接接続
      → 許可されたサーバー

HTTP 転送と CONNECT に対応します。CONNECT は TLS を復号せず、アプリと外部サーバーの間で TLS を終端します。SSH ポート転送や接続先からクライアントへの新規 TCP 到達性は要求しません。

接続先は Linux/Windows、bridge は Linux/Windows/macOS に対応します。機能は既定無効です。これはプロキシ対応アプリ向けの経路であり、OS 全体のネットワーク隔離は行いません。

## 2. 起動と公開インターフェース

### CLI

- bridge に --proxy と反復可能な --proxy-allow-host を追加します。
- 接続先に --client-proxy を追加します。
- bridge は明示有効化と1件以上の許可規則を必須とし、設定漏れ・無効な規則は起動エラーにします。
- 両端の明示有効化と版1の能力交渉を必要とします。片側だけ有効、相手非対応、版不一致は起動エラーです。
- --no-transfer と併用できます。プロキシとファイル転送は独立しています。
- 無効時は通常の MCP stdio を維持します。

起動例:

    host-shell bridge --proxy --proxy-allow-host 'packages.example.com:443' --       ssh -T target /path/to/host-shell --mcp --client-proxy

### proxy_status

bridge 専用の読み取り専用ツールとして、有効時だけ公開します。接続先の --tools とは独立して扱います。

入力は after_seq (既定0、非負)、limit (既定20、1〜100) です。指定連番より後の結果を昇順で取得します。

出力は enabled、state、allow_hosts、active_connections、events、next_seq、truncated とします。events は seq、time (RFC3339)、connection_id、host、port、status、reason を持ちます。status は allowed/denied/failed とし、ポリシー拒否・認証失敗・接続上限・DNS/接続/上流障害などを区別します。

直近100件をリングで保持し、履歴脱落やページ上限で未返却の結果がある場合は truncated を示します。next_seq は最後に返した連番、空の場合は入力値です。連続する認証失敗は集約し件数を示します。

sys_get_info は接続先のプロキシ状態と URL ファイルのパスを案内します。認証付き URL 本体は返しません。Instructions と help から proxy_status の診断方法を案内します。

## 3. 通信と HTTP 処理

### 共通通信モジュール

internal 以下に共通モジュールを設け、MCP Connection をラップします。専用 JSON-RPC 通知を SDK 到達前に分離し、通常 MCP はそのまま流します。独自通知はエージェント側へ公開しません。

通知名は host-shell/proxy/* とし、hello、ready、open、open_result、data、window、half_close、close を用います。hello/ready で版1を交渉し、正常完了後にリスナーと通常サービスを利用可能にします。対向の通常 initialize が先に届く場合も、必要な交渉を確認できなければ起動エラーにします。

open は接続先から送信し、接続 ID、正規化した host と port、HTTP/CONNECT の区分を持ちます。ID はセッション内で再利用しません。open_result は成功または機密情報を含まない失敗コード・理由を返します。

data は標準 Base64 のペイロードです。window は受信処理済みバイト数に応じた追加送信権、half_close は片方向 EOF、close は接続全体の終了を通知します。各接続のデータと EOF の順序を維持します。

接続待ち・通信中・片方向終了・終了の遷移、接続 ID、フレームサイズ、Base64、ウィンドウ値を検証します。不正な通知で別接続を操作したり、任意サイズのメモリーを割り当てたりしません。終了の競合は冪等に処理します。

標準出力は JSON 行専用です。専用通知のフレーム制限は既存 MCP の許容メッセージサイズを縮小しません。

### 接続先 HTTP プロキシ

127.0.0.1 の動的ポートで待ち受け、セッション別暗号学的乱数を用いた Proxy-Authorization の Basic 認証を要求します。認証情報は外部・上流へ転送しません。

HTTP の宛先ごとに許可を検査し、本文をストリーミングします。hop-by-hop ヘッダーとプロキシ認証を除去し、不正な要求・宛先不一致を拒否します。中継自身はリダイレクトを追跡せず、アプリからの次の要求で宛先を再検査します。

CONNECT は許可と接続確立の後に成功応答を返し、以降は双方向のバイト列を転送します。CONNECT は許可ポートへの HTTPS 以外の TCP 通信にも使用可能です。

拒否は403、認証失敗は407、上限超過は503、接続失敗は502、確立タイムアウトは504を基本とします。CONNECT 成功後の障害は接続を終了し、診断へ記録します。

### クライアント側の経路

クライアント起動時の HTTP_PROXY/HTTPS_PROXY/NO_PROXY と小文字版を使用します。HTTP 転送と上流 CONNECT に対応します。上流 URL の資格情報はその上流への認証だけに使用し、診断に出しません。上流が HTTPS の場合も標準の証明書検証を行います。

接続先のプロキシ環境はクライアントにコピーしません。上流設定が不正、または接続に失敗した場合に直接通信へ自動切替しません。

## 4. 制限・診断・機密情報

### 許可リスト

bridge が最終要求先のホスト名 glob と任意のポートを検査します。CIDR と Unix ソケット規則は受理しません。既存のホスト名・ポート照合を共用し、既存 --allow-host の意味を変更しません。

これは要求された名前の制限であり、名前解決後の IP の範囲を保証しません。内部 IP は一律禁止しません。上流プロキシ自身は起動環境で指定した経路として扱い、許可リストは最終要求先へ適用します。

stderr と診断リングには宛先・結果・理由を記録します。本文、URL パス・クエリー、認証トークン、上流資格情報は記録しません。認証失敗の連続ログを集約し、出力を無制限に増やしません。proxy_status にも通常の出力上限を適用します。

### 環境変数

セッション情報として設定を保持し、プロセス全体の os.Setenv は使いません。

通常の exec_run/job_start は継承環境の HTTP_PROXY/HTTPS_PROXY/http_proxy/https_proxy を認証付き中継 URL に置換し、NO_PROXY/no_proxy は維持します。自動設定の後に --unset-env、最後に呼び出しの env を適用します。Windows では環境変数名の大小文字を同一視し重複を避けます。

net_request_http は明示 proxy/none を優先し、省略時だけセッション中継 URL と NO_PROXY を使います。グローバルな環境プロキシ解決のキャッシュに依存しません。Unix ソケットは直接接続です。既存のネットワーク・ファイル制限も維持します。

exec_sudo は sudo の環境規則に従い、自動伝播を保証しません。既存の別プロセスの環境は変更しません。

### URL ファイルとマスク

接続先のセッション別一時ディレクトリに認証 URL を UTF-8 テキストで保存します。Linux はディレクトリ0700・ファイル0600、Windows は現在ユーザー限定の DACL とします。権限を確保できなければ起動失敗にします。

URL は http://ユーザー:トークン@127.0.0.1:ポート の形式です。通常終了・切断・起動失敗でファイルを削除します。強制終了後にファイルが残っても、終了セッションの情報で新しいセッションを使用できません。

既知のセッション秘密としてトークン・認証 URL・認証ヘッダーを通常ツール結果・進捗・監査でマスクします。通常の出力マスク設定の有無にかかわらず適用します。URL ファイルを読むツールでも本文の秘密を会話に表示しません。同一 OS ユーザーが直接ファイルから利用することは許可します。

## 5. 負荷・障害・終了

- セッション最大32接続とし、接続待ちも枠に含めます。超過は明示的に拒否します。
- data は復号後16KiB以下、片方向送信ウィンドウ64KiBです。送信権がなければネットワーク側の読み取りを待たせます。
- キューは有限とし、通常 MCP と制御を中継データより優先します。MCP の順序と各接続のバイト順序を維持します。
- 接続確立・HTTP ヘッダー受信は30秒、通信無進行は5分、終了待ちは5秒です。テストでは時計等を注入し短時間で検証します。
- 閉塞した1接続のキュー投入で MCP 読み取りループや他接続を無制限に停止させません。
- EOF・context キャンセル・異常終了時は全接続、待ち受け、待機処理、goroutine、認証ファイルを終了・解放します。
- 自動再試行・切断後の継続・直接経路への自動フォールバックは行いません。
- 無効時は待ち受け・環境変更とも行いません。env、proxy:none、NO_PROXY による明示的な直接通信は維持します。

## 6. 実装単位・文書反映

共通モジュールに多重化、状態、フロー制御を集約します。bridge は許可検査・外向き接続・上流処理・proxy_status を、接続先は認証リスナー・HTTP 処理・環境情報提供を担当します。

起動設定、server 組み立て、proc の環境作成、HTTP ツール、sys_get_info、出力マスク・監査と連携します。既存転送機能と既存ツールの命名は維持します。

README、日英の利用・運用・リファレンス・開発文書、埋め込み help、接続スキルへ、起動例、通信元、許可規則、拒否診断、認証情報の扱い、対応範囲を反映します。既存 SSH stdio を利用する経路を図示します。

## 7. 受入条件

1. HTTP の本文・バイナリ・大きなファイル、CONNECT の TLS 往復・双方向・片方向終了を確認します。TLS 証明書を差し替えません。
2. クライアントの上流 HTTP/HTTPS プロキシ、上流認証、NO_PROXY、上流障害をローカル試験サーバーで確認します。
3. ホスト glob・ポートの許可拒否、CONNECT 拒否、認証失敗、接続上限と proxy_status の理由・ページング・履歴脱落を確認します。
4. 子プロセス環境、大小文字、env、--unset-env、NO_PROXY、明示 proxy/none、Unix ソケット、sudo の適用範囲を確認します。
5. URL ファイルの権限・削除と、結果・監査・進捗・stderr からの資格情報漏えい防止を確認します。
6. 過大・不正フレーム、Base64、ID・遷移・送信権の不正、遅い読み手、32接続と超過、タイムアウト、キャンセル、切断、起動途中失敗、終了の冪等性を検証します。
7. 同時 MCP 呼び出しが進行し、キュー・メモリー・goroutine が増え続けないことを確認します。
8. 通常ツール、resources、確認、進捗、キャンセル、ファイル転送が有効/無効の双方で維持されます。
9. 無効、片側有効、版不一致を検証します。インメモリと実 stdio 子プロセスの結合テストで JSON-RPC の非混線を確認します。
10. make、6ターゲットのクロスビルド、現行全 OS CI を確認します。Windows の DACL・環境と macOS bridge も対象です。未実施の検証は受入前に明示して扱いを確認します。

実装後は受入条件を照合し、残課題を整理し、成果物・検証結果を提示してユーザーの受入承認を求めます。
