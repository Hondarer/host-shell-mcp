## 調査結果

### 原因の確認

`Manager.socks` は、要求の一部だけを読んで拒否の応答を書き、そのまま接続を閉じる経路を持ちます。受信して読んでいないデータが残った接続を閉じると、OS は切断の合図 (FIN) ではなく、接続のリセット (RST) を送ります。Windows は RST を受けると、クライアントがまだ読んでいない受信データ (拒否の応答) を捨てます。Linux は受信済みのデータを先に読ませるため、問題が表に出ません。

作業用の一時フォルダーに複製したリポジトリで、クライアントが応答を読む前に 100 ミリ秒待つテストを作り、Windows 向けに作って作業環境の Windows で実行しました。

| 経路 | 修正前 (Windows) | 修正前 (Linux) | 試作の修正後 (Windows) |
| --- | --- | --- | --- |
| SOCKS4 の要求 (9 バイトのうち 2 バイトだけ読む) | 20 回中 20 回、接続のリセットで失敗 | 成功 | 20 回中 20 回成功 |
| SOCKS5 の未対応のアドレス種別 (アドレスと port を読まない) | 20 回中 20 回、接続のリセットで失敗 | 成功 | 20 回中 20 回成功 |

CI の `TestSOCKS` は待たずにすぐ読むため、まれ (約 1,300 回中 1 回) にしか失敗しませんでした。

### 拒否の応答を書いて閉じる経路

`Manager.socks` で、応答を書いた後に閉じる経路は次のとおりです。

| 経路 | 応答 | 読み残し |
| --- | --- | --- |
| SOCKS4/4a の要求 | `0x5b` (拒否) | 必ず残る (要求の残り) |
| 認証なしの方式を含まない | `0xff` | 通常は残らない |
| 未対応のアドレス種別 | `0x08` | 必ず残る (アドレスと port) |
| 未対応のコマンド (BIND など)、宛先の形式の誤り、許可規則による拒否、接続先での失敗、接続数の上限 | 各コード | 通常は残らない。クライアントが応答を待たずにデータを送った場合は残る |

Table: 応答を書いて閉じる経路

### 試作した修正

応答を書いた後、すぐに閉じずに、書き込み側だけを閉じ (`CloseWrite`、相手に FIN が届きます)、残りの受信データを期限付きで読み捨ててから閉じます。この方法は一般に lingering close と呼ばれます。Go の `net/http` のサーバーも、エラーの応答の後に同じ目的で書き込み側を閉じて待ちます。

```go
// lingerClose closes c after a reply so that unread request bytes do not make the OS
// reset the connection, which on Windows discards the reply before the client reads it.
func lingerClose(c net.Conn) {
	if cw, ok := c.(interface{ CloseWrite() error }); ok {
		cw.CloseWrite()
	}
	c.SetReadDeadline(time.Now().Add(time.Second))
	io.Copy(io.Discard, io.LimitReader(c, 64<<10))
	c.Close()
}
```

クライアントは応答と FIN を受け取って通常は接続を閉じるため、読み捨ては多くの場合すぐに終わります。

### 対象外とした箇所

- 接続先の client-proxy (`internal/clientproxy/target.go`) は、Go の `net/http` のサーバーで応答し、閉じる前の処理を `net/http` が行います。
- client-proxy のゲートウェイ (`internal/clientproxy/gateway.go`) の 502 の応答は、TCP ではなく MCP のチャネルの中の通り道に書くため、この問題は起きません。
- bridge のローカル転送 (SOCKS でないもの) は、接続先での接続に失敗すると、何も書かずに閉じます。捨てられる応答がないため、クライアントには切断がリセットとして見えるだけです。

**Question**

**Context**

原因は、読み残しのある接続を閉じるとリセットが送られることです ([原因の確認](#原因の確認))。直し方は 2 つあります。

```text
A: 閉じ方を直す (lingering close)
   応答を書いた後、書き込み側を閉じ、残りの受信を期限付きで読み捨ててから閉じます。
   読み残しの量や要求の形式に関係なく効きます。試作で効果を確認済みです。
```

### Q-002 適用する経路

### Q-003 読み捨ての期限

**Status**

解決済み

**Question**

閉じる前に残りの受信を読み捨てる時間の上限を、どれにしますか？

**Context**
