### Q-024 入力の終端後の応答の扱い

**Status**

解決済み

**Question**

`host-shell --mcp` は、標準入力が終端に達した後、受信済みの要求の応答をどう扱いますか。

**Context**

[Q-019](#q-019-標準入力の終端で応答が失われる挙動の扱い) の回答「今回の案件で修正する。より良い形に改善したい」を受けた質問です。原因は Q-019 の Assessment のとおりで、修正は `host-shell` の側 (標準入出力を包む `internal/channel` の層) で行えます。入力の終端を SDK へ伝える前に、受信済みの要求の応答が書き終わるのを待ちます。

判断が必要なのは、SSH の切断との区別です。`host-shell` は、標準入力の終端を SSH の切断として扱い、実行中のコマンドとジョブを止めます。これは文書に書いている約束です。応答を待つようにすると、切断のときにも、実行中のコマンドが完了またはタイムアウトするまで残ります。

```text
単発の利用:  printf '%s\n' "$INIT" "$INITIALIZED" "$CALL" | ssh -T target host-shell --mcp
             (入力だけが閉じ、出力は開いている。応答を待ってほしい)
SSH の切断:  入力と出力の両方が閉じる。実行中のコマンドをすぐ止めてほしい
```

| 案 | 単発の利用 | SSH の切断時 | 未確認の点 |
| --- | --- | --- | --- |
| A | 起動オプションを付けたときだけ応答を待つ | 既定では現在と同じ (すぐ止める) | なし |
| B | 既定で応答を待つ | 出力の切断を監視し、切断ならすぐ止める | Windows で出力の切断を検知できるか (Linux は `poll` で検知できる見込み) |
| C | 既定で応答を待つ | 実行中のコマンドが完了またはタイムアウトするまで残る | なし |

Table: 入力の終端後の扱いの比較

どの案でも、応答を書けないまま終了する場合は、終了コードを 0 以外にして標準エラーに理由を出力します (現在は終了コード 0 で何も出力しません)。

**Answer**

選択方式: 単一選択

- [x] A: (推奨) 起動オプション (名前は最終仕様で提示) を付けたときだけ、応答を書き終えてから終了する。既定の動作は変えない。
- [ ] B: 既定で応答を書き終えてから終了し、出力の切断を検知した場合はすぐ止める。Windows で検知できない場合は、作業を中断して再度確認する。
- [ ] C: 既定で応答を書き終えてから終了する (切断の検知はしない)。
- [ ] D: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)
