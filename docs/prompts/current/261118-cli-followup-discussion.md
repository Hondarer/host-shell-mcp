### Q-001 agy での検証の方法

**Status**

回答済み

**Question**

agy からの操作の検証 (BL-001) は、どの方法で行いますか。

**Context**

前回の検証では、承認を一律に省略するオプションでの実行が作業環境で拒否されたため、他のエージェントは `host-shell` だけを許可して実行しました。agy にも同じ形の設定があることが分かりました。

```text
A: PATH=<host-shell を置いたディレクトリ>:$PATH agy -p "<他のエージェントと同じ 7 段階の指示>" \
     --settings '{"agentMode": "", "permissions": {"allow": ["command(host-shell)"]}}'
   (Default モードで、host-shell のコマンドだけを承認なしで実行する。設定は保存されない)
B: 利用者が agy を対話的に起動し、各コマンドを承認しながら 7 段階を実行する
```

**Answer**

選択方式: 単一選択

- [ ] A: (推奨) `--settings` で `host-shell` だけを許可し、Default モードで非対話に実行する。
- [ ] B: 利用者が対話的に承認しながら実行する。
- [ ] C: 検証せず、未検証のままとする (残課題を閉じる)。
- [x] D: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足: --dangerously-skip-permissions を利用してよい

**Recommendation**

推奨: A  
理由: 他のエージェントと同じ条件 (MCP なし、`host-shell` だけを許可) で比べられ、利用者の操作も要りません。Auto モードは承認を自動で判断するため使いません。A が作業環境で拒否された場合は、B を利用者に依頼します。

### Q-002 実行権限の修正の範囲

**Status**

回答済み

**Question**

スクリプトの実行権限の修正 (BL-002) は、どの範囲で行いますか。

**Context**

不具合は、手元で直接実行する `host-shell-vscode-remote-ssh/scripts/client/fetch.sh` と `ssh-key.sh` に実行権限がないことです。他の 100644 のスクリプトは、接続先で `sh` か `bash` を付けて実行するもの、または読み込まれるもので、実行権限がなくても動きます。

```text
A: client/fetch.sh と client/ssh-key.sh を 100755 にする。CI に「.agents/skills の .sh はすべて 100755」の検査を加え、
   検査を通すため他の 100644 の .sh も 100755 にそろえる (動作は変わらない)
B: client/fetch.sh と client/ssh-key.sh だけを 100755 にする (CI の検査は加えない)
```

**Answer**

選択方式: 単一選択

- [x] A: (推奨) すべての `.sh` を 100755 にそろえ、CI に検査を加える。
- [ ] B: 2 つのスクリプトだけを直す。
- [ ] C: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足:

**Recommendation**

推奨: A  
理由: 「直接実行するか」を区別せずに一律の規則にすると、新しいスクリプトを加えるときの見落としを CI で防げます。実行権限を付けても、`sh` を付けた実行や読み込みの動作は変わりません。

### Q-003 承認が必要な制限の範囲

**Status**

回答済み

**Question**

code-server スキルの手順 1.4 で、利用者の承認が必要な `restrictions` の範囲は、どれにしますか。

**Context**

検証を実行したエージェントは、`restrictions` が伏せ字 (`--redact`) だけの場合も承認が必要かで迷いました。code-server の端末とファイル操作は `host-shell` を通らないため、伏せ字も確認 (`--confirm`) も働かず、操作ログにも残りません。

**Answer**

選択方式: 単一選択

- [x] A: (推奨) 現在の規則 (空でなければ承認が必要) を保ち、伏せ字と確認を含むすべての項目が対象であることと、その理由 (端末では働かない) を明記する。
- [ ] B: 伏せ字だけの場合は承認を不要にする。
- [ ] C: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足:

**Recommendation**

推奨: A  
理由: 接続先の管理者が伏せ字を指定したのは、出力の機密をエージェントに見せないためです。code-server の端末はその意図を通らないため、利用者の判断を求めるのが安全です。

### Q-004 設定の写しの保存先の接続先名

**Status**

回答済み

**Question**

code-server の設定の写しの保存先 `~/.config/host-shell-code-server/<target name>/config.yaml` の `<target name>` は、何にしますか。

**Context**

スキルと文書 (`docs/ja/code-server.md` の `<接続先名>`) に定義がなく、検証のエージェントは SSH の別名を使いました。接続先ごとに別のパスワードが生成されるため、接続先を区別できる名前である必要があります。

```text
A: エージェントの登録名 (MCP の場合、例: host-shell-target)。CLI の場合はセッションの名前 (例: default)。
   名前が `default` などで接続先を区別できない場合は、利用者と短い名前を決める
B: 経路の最後の SSH ホスト名 (例: target)。コンテナーの場合はコンテナー名
```

**Answer**

選択方式: 単一選択

- [x] A: (推奨) エージェントの登録名またはセッションの名前とし、区別できない場合は利用者と決める。
- [ ] B: 経路の最後の SSH ホスト名またはコンテナー名とする。
- [ ] C: その他
- [ ] X: 意図不明 (詳細な質問内容に再生成すること)

その他の回答 / 補足:

**Recommendation**

推奨: A  
理由: 登録名やセッションの名前は、利用者が接続先を呼ぶ名前で、エージェントが確実に知っています。経路の最後のホスト名は、多段の経路や別名の付け方によって、エージェントが正しく取り出せない場合があります。
