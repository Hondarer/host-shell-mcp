## BL-001 Windows のクライアントと Tera Term での実機検証が未実施

### 概要と問題点

- **現状の事象**: `host-shell.exe connect` を Windows の OpenSSH と Git for Windows の OpenSSH の `ProxyCommand` として使う構成、Windows のパスワード ファイルのアクセス許可の判定、端末での入力 (コンソールのエコー停止)、Tera Term (種別 HTTP) との併用を実機で確かめていない。`docs/ja/ssh-proxy.md` の検証済みの範囲では「未検証」としている。
- **本来あるべき姿**: 最終仕様の受入条件 (Windows の実機) を満たし、文書の該当行が「検証済」になる。

### 経緯と見送り理由

- **摘出契機**: 実施時。Windows の検証環境 (Hyper-V の仮想マシン) は Windows のホストから操作する構成で、WSL のセッションからは届かない。
- **今回の見送り理由**: Windows 側のセッションでの作業が必要。手順は [検証記録の「Windows の実機」](261113-ssh-proxy-validation.md#windows-の実機-手順未実施) に用意した。

### 影響範囲とリスク

- **影響対象**: Windows のクライアントの利用者 (Tera Term を使っている主な利用者層)。
- **放置した場合のリスク**: Win32-OpenSSH が `ProxyCommand` に渡すパイプ (非同期 I/O 用) の読み書き、パス区切り、ACL 判定の誤りが、利用者の環境で初めて見つかる。

### 推奨される対応策

- **恒久対応案**: 検証記録の手順で確認し、結果を検証記録と `docs/ja/ssh-proxy.md`・英訳の検証済みの範囲に反映する。
- **参考情報**: [最終仕様の受入条件](261113-ssh-proxy-design.md#受入条件)、`internal/routeproxy/perm_windows.go`、`internal/routeproxy/tty_windows.go`

## BL-002 Windows・macOS での internal/routeproxy の自動テストが未実行

### 概要と問題点

- **現状の事象**: `go vet` は 3 つの OS で成功しているが、テストの実行は Linux だけである。`perm_windows_test.go` (アクセス許可の判定) は Windows でしか動かない。
- **本来あるべき姿**: CI (ubuntu、windows、macos) でテストが成功する。

### 経緯と見送り理由

- **摘出契機**: 実施時。
- **今回の見送り理由**: CI はプッシュで動くため、コミットとプッシュの承認後に確認する。

### 影響範囲とリスク

- **影響対象**: `internal/routeproxy`
- **放置した場合のリスク**: Windows の SDDL・ACL の扱いの誤りが見逃される。

### 推奨される対応策

- **恒久対応案**: ブランチをプッシュして CI の結果を確認し、失敗があれば修正する。
- **参考情報**: `.github/workflows/ci.yml`

## BL-003 SOCKS・TELNET 形式のプロキシに対応していない

### 概要と問題点

- **現状の事象**: `host-shell connect` は HTTP `CONNECT` だけに対応し、`-S`・`-s`・`-T`・`-t`・`-c` などはエラーになる。Tera Term と connect.c は SOCKS4/5 と TELNET 形式にも対応している。
- **本来あるべき姿**: 利用者の環境で SOCKS が使われている場合に、同じ互換の範囲で使える。

### 経緯と見送り理由

- **摘出契機**: 前提検討時 (Q-001)。
- **今回の見送り理由**: 要求の対象が HTTP CONNECT の Basic 認証であるため。

### 影響範囲とリスク

- **影響対象**: SOCKS プロキシを使う環境の利用者。
- **放置した場合のリスク**: 該当環境では OpenSSH の他の手段 (`nc -X 5` など) が必要になる。

### 推奨される対応策

- **恒久対応案**: 要望が出た時点で、SOCKS5 (ユーザー名・パスワード認証) から追加する。検証には SOCKS サーバーのコンテナーを用意する。
- **参考情報**: connect.c の `-S`、`SOCKS5_USER`、`SOCKS5_PASSWD`

## BL-004 Basic 以外のプロキシ認証 (NTLM、Negotiate、Digest) に対応していない

### 概要と問題点

- **現状の事象**: 企業のプロキシには NTLM や Negotiate (Kerberos) を要求するものがある。`host-shell connect` とインターネット向けプロキシ (`bridge`) のどちらも Basic だけに対応する。
- **本来あるべき姿**: Windows の統合認証のプロキシでも、追加の中継なしで接続できる。

### 経緯と見送り理由

- **摘出契機**: 前提検討時 (Q-002)。
- **今回の見送り理由**: Go の標準ライブラリが対応しておらず、外部ライブラリと Windows の SSPI が必要なため。文書では、cntlm などのローカル中継を挟む方法に触れている (未検証)。

### 影響範囲とリスク

- **影響対象**: NTLM・Kerberos のプロキシを使う環境。
- **放置した場合のリスク**: 利用者がローカル中継を自分で用意する必要がある。

### 推奨される対応策

- **恒久対応案**: まず cntlm などの迂回を検証して文書を「検証済」にする。需要があれば SSPI による Negotiate を設計する。
- **参考情報**: `docs/ja/ssh-proxy.md` の「制限」

## BL-005 2 段目以降の区間にある SSH 経路プロキシを扱えない

### 概要と問題点

- **現状の事象**: 対象はクライアントから 1 段目の区間だけで、中継サーバーから先の区間にあるプロキシは扱えない。
- **本来あるべき姿**: 中継サーバーの `~/.ssh/config` にも `ProxyCommand` を置いて、任意の区間でプロキシを通せる。

### 経緯と見送り理由

- **摘出契機**: 前提検討時 (Q-007)。
- **今回の見送り理由**: 中継サーバーへの実行ファイルと資格情報の配置は、リスクと手順の両面で別の判断が必要なため。

### 影響範囲とリスク

- **影響対象**: 中継サーバーの先にプロキシがある環境。
- **放置した場合のリスク**: その環境では host-shell に接続できない。

### 推奨される対応策

- **恒久対応案**: 中継サーバーへの `host-shell` の配置 (`deploy.sh` の応用) と、資格情報の置き場所・権限の方針を設計する。
- **参考情報**: Q-007

## BL-006 パスワードの入力手段が端末とファイル・環境変数に限られる

### 概要と問題点

- **現状の事象**: `SSH_ASKPASS` と OS の資格情報ストア (Windows 資格情報マネージャー、macOS キーチェーン、libsecret) に対応していない。パスワード ファイルは平文である。
- **本来あるべき姿**: 平文のファイルを置かずに、MCP の構成 (端末なし) でも資格情報を渡せる。

### 経緯と見送り理由

- **摘出契機**: 前提検討時 (Q-005)。
- **今回の見送り理由**: 3 つの OS それぞれの実装と検証が必要なため。

### 影響範囲とリスク

- **影響対象**: パスワードの平文保存が許されない環境。
- **放置した場合のリスク**: 運用規程によっては利用できない。

### 推奨される対応策

- **恒久対応案**: Windows 資格情報マネージャーから読む `--credential-target` のようなオプションを検討する。
- **参考情報**: Q-005
