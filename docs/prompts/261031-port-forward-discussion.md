## 対象と参照資料

対象成果物: SSH ポート転送を使えない環境で、既存 SSH セッションの標準入出力 (stdio) を通じて TCP のローカル転送・リモート転送・クライアント側 SOCKS5 を提供する機能と、その利用・運用・開発文書です。

今回の対象範囲: ローカル転送・リモート転送・クライアント側 SOCKS5 の TCP 通信 ([Q-001](#q-001-転送方向の範囲)、[Q-002](#q-002-動的転送の扱い)、[Q-003](#q-003-転送できる通信の種別))。

書き込み可能な検討用 Markdown: この文書 (`docs/prompts/261031-port-forward-discussion.md`)

参照資料と版: ブランチ codex/client-http-proxy のコミット b85d95652ede3f0b1b0666893e09f744fc24acf4 を調査基準とします。成果物の作成は PR #1 のマージ後の main を基準とします ([Q-013](#q-013-作業ブランチと-pr))。

- [internal/clientproxy/channel.go](../../internal/clientproxy/channel.go): MCP の Connection をラップし、`host-shell/proxy/*` 通知 (hello、ready、open、open_result、data、window、half_close、close) で TCP 相当のストリームを多重化します。データは Base64、16KiB/フレーム、片方向 64KiB のウィンドウ、最大 32 接続です。
    - `open` は接続先 (target) だけが送信し、bridge だけが受理します (`handle` は `c.remote` のとき `open` を拒否)。接続 ID の採番も接続先側 (`c.next`) だけです。ストリームの向きが一方向に固定されています。
    - hello/ready は版番号だけを交換し、機能の一覧を持ちません。チャネルは bridge の `--proxy` と接続先の `--client-proxy` の両方が指定された場合だけ構成されます。
- [internal/clientproxy/gateway.go](../../internal/clientproxy/gateway.go): bridge 側で宛先許可 (ホスト glob と任意のポート)、HTTP 転送、CONNECT による TCP 中継、上流プロキシ、診断リング (proxy_status) を担当します。CONNECT 中継 (`tunnel`) には通信無進行 5 分のタイムアウトがあります。接続先の監査ログへの記録はありません。
- [internal/clientproxy/target.go](../../internal/clientproxy/target.go): 接続先側で 127.0.0.1 の認証付き HTTP プロキシを待ち受けます。
- [internal/bridge/bridge.go](../../internal/bridge/bridge.go): `--proxy`、`--proxy-allow-host` と proxy_status ツールを提供します。
- [internal/policy/policy.go](../../internal/policy/policy.go): 接続先の `--allow-host` (`CheckHost`) はネットワーク ツールの宛先制限です。
- [docs/ja/client-proxy.md](../ja/client-proxy.md): 既存 HTTP プロキシの正本文書です。
- [docs/ja/operations.md](../ja/operations.md): `authorized_keys` の `command=` と `no-port-forwarding` で、host-shell を介さないポート転送を防ぐ運用を案内しています。
- [docs/ja/user-guide.md](../ja/user-guide.md): 「ポート転送 (`-L`、`-R`、`-D`、`ProxyJump`、`-W`) や SFTP は使用しません」と記載しています。
- PR #1 (ドラフト、codex/client-http-proxy): HTTP プロキシ機能は main 未マージかつ未リリースです。2026-10-31 09:58 JST 時点でドラフトのまま未マージであり、別案件 (261031-client-proxy) の成果物の受入承認待ちです。

## ユーザーが明示した要求

本対話の依頼 (2026-10-31、Tetsuo Honda) を根拠とします。

- クライアントからの Web 要求を接続元から発信できる既存機能 (クライアント経由 HTTP プロキシ) をさらに拡張します。
- SSH のポート転送ができない環境でも、疑似的に双方向にポート転送する機能を追加します。
- agree-before-implement スキルを使用し、計画ファイルは docs/prompts に置きます。

用語は次のとおりとします。

| 用語 | 待ち受け側 | 発信側 | ssh の相当 |
| --- | --- | --- | --- |
| ローカル転送 | クライアント (bridge) | 接続先 (host-shell --mcp) | `-L` |
| リモート転送 | 接続先 (host-shell --mcp) | クライアント (bridge) | `-R` |
| SOCKS (クライアント側) | クライアント (bridge) | 接続先 (host-shell --mcp)、宛先は接続ごと | `-D` |

第 1 群の回答 (2026-10-31 09:58:33 JST、Tetsuo Honda) で次を確定しました。

- ローカル転送とリモート転送の両方を実装します ([Q-001](#q-001-転送方向の範囲))。
- クライアント側で待ち受ける SOCKS5 (`-D` 相当) を範囲に含めます。詳細は第 2 群で確認します ([Q-002](#q-002-動的転送の扱い))。
- 転送対象は TCP だけとし、Unix ドメイン ソケットと UDP は対象外です (BL-001) ([Q-003](#q-003-転送できる通信の種別))。
- 転送は bridge の起動オプションで常設でき、MCP ツールでも許可範囲内で追加・削除できます ([Q-004](#q-004-転送の定義方法))。
- 接続先側の明示有効化は方向ごとの別オプションとし、`--client-proxy` とは独立させます ([Q-005](#q-005-接続先側の有効化の単位))。
- ローカル転送で接続先が発信する宛先に接続先の既存 `--allow-host` を適用します ([Q-006](#q-006-接続先から発信する宛先の制限))。
- 接続先で待ち受けるポート番号は制限しません (BL-002) ([Q-007](#q-007-接続先で待ち受けるポートの制限))。
- 待ち受けは両側ともループバックに限定し、既定 127.0.0.1、`::1` の指定を許可します ([Q-008](#q-008-待ち受けアドレス))。
- ポート転送の待ち受けへの同一ホスト他ユーザーからの無認証接続を、ssh と同等の性質として容認し文書に明記します ([Q-009](#q-009-待ち受けポートの無認証接続))。
- sshd の転送禁止設定は検出せず、本機能 (HTTP プロキシを含む) がそれでは止められないことを文書に明記します ([Q-010](#q-010-sshd-の転送禁止との関係))。
- 多重化を汎用パッケージへ分離し、HTTP プロキシとポート転送が共用します ([Q-011](#q-011-共通通信基盤の構成))。
- 通信プロトコルは版 1 のまま定義を改めます ([Q-012](#q-012-通信プロトコルの改訂))。
- 成果物の作成は PR #1 が main へマージされた後、main から分岐して行います ([Q-013](#q-013-作業ブランチと-pr))。
- 対応 OS は既存構成と同じ全 OS です ([Q-014](#q-014-対応-os))。

第 2 群の回答 (2026-10-31 10:08:45 JST、Tetsuo Honda) で次を確定しました。

- 通知名を `host-shell/channel/*` へ変更し、リリースの有無にかかわらず版 1 のまま定義を改めます ([Q-015](#q-015-通知名の変更)、[Q-016](#q-016-版-1-を維持する前提の変化))。
- 接続先の転送オプションを「許可」、bridge のその方向の常設転送または許可規則を「要求」として照合します。許可のない要求は起動エラー、許可だけなら正常起動、要求がなければ通常の MCP です。HTTP プロキシは両端必須を維持します ([Q-017](#q-017-機能の要求と許可の照合))。
- bridge の常設転送は `--forward-local [BIND:]PORT:HOST:HOSTPORT`、`--forward-remote [BIND:]PORT:HOST:HOSTPORT`、`--forward-socks [BIND:]PORT` (反復可能、BIND は 127.0.0.1 または `[::1]`、PORT 0 は自動割当) です ([Q-018](#q-018-bridge-の常設転送オプションの書式))。
- 接続先の許可オプションは `--allow-forward-local`、`--allow-forward-remote` (値なし) です。SOCKS は `--allow-forward-local` で許可され、各接続の宛先に `--allow-host` を適用します ([Q-019](#q-019-接続先の有効化オプションの名前)〜[Q-021](#q-021-socks-の宛先への接続先制限))。
- SOCKS5 は CONNECT だけ、アドレスは IPv4・IPv6・ドメイン名 (接続先で名前解決)、認証なしです ([Q-022](#q-022-socks-のプロトコル範囲)、[Q-023](#q-023-socks-の認証))。
- bridge の `--forward-allow-local HOST[:PORT]`、`--forward-allow-remote HOST[:PORT]` がツール作成の転送と SOCKS の各接続の宛先を制限します。常設のローカル・リモート転送は照合を省き、SOCKS には 1 件以上の `--forward-allow-local` が必須です。クライアント側の待ち受けポートは制限しません ([Q-024](#q-024-ツールで作成する転送の許可規則)〜[Q-026](#q-026-クライアント側の待ち受けポートの制限))。
- ツールは forward_open、forward_close (常設は対象外、既存接続も切断)、forward_status とし、規則に応じて公開します ([Q-027](#q-027-転送ツールの構成)、[Q-028](#q-028-転送ツールの公開条件))。
- 同時接続は全機能共有で 64、転送は合計 16 までです。ポート転送と SOCKS に無通信タイムアウトは設けず、HTTP プロキシは 5 分を維持します ([Q-029](#q-029-同時接続数の上限)〜[Q-031](#q-031-無通信タイムアウト))。
- 常設転送の待ち受け失敗は起動エラーです。発信失敗はポート転送では接続を閉じ、SOCKS5 では応答コードを返します。確立待ちは 30 秒です ([Q-032](#q-032-常設転送の待ち受け失敗)、[Q-033](#q-033-発信失敗時の動作))。
- forward_status の履歴は proxy_status と同じ形式で別に保持します。接続先の監査ログに転送の待ち受けと発信を記録し、sys_get_info に許可方向と待ち受け中のリモート転送を追加します ([Q-034](#q-034-診断の形式)〜[Q-036](#q-036-接続先の-sys_get_info))。
- 文書は docs/ja/port-forward.md と英訳を新設し、関連文書を更新します ([Q-037](#q-037-文書の構成))。

第 3 群の回答 (2026-10-31 10:20:41 JST 確認、Tetsuo Honda) で次を確定しました。

- リモート転送で bridge は上流プロキシを使用せず、宛先へ直接接続します ([Q-040](#q-040-リモート転送の発信経路))。
- 受入条件は [Q-041](#q-041-受入条件) の 10 項目とします。

### Q-004 転送の定義方法

**Status**

解決済み

**Question**

転送の追加・削除は、bridge の起動オプションと MCP ツールのどちらで行いますか？

**Context**

ssh は接続時のオプション (`-L`/`-R`) で転送を定義します。本機能では次の選択肢があります。いずれの案でも、転送の要求元はクライアント (bridge) 側とし、接続先から転送を開始させることはしない想定です。

- 起動オプションだけ: 利用者が MCP サーバー登録時に転送を固定します。エージェントは転送を変更できません。転送を変える際は bridge (多くのクライアントではエージェントのセッション) の再起動が必要です。
- MCP ツール: エージェントが実行中に転送を追加・削除できます。例えば接続先で開発サーバーを起動してからローカル転送を作成できます。エージェントが利用者の想定外の転送を作らないよう、起動オプションで許可範囲を定める必要があります (第 2 群で詳細化)。

```text
案 A: 起動オプションだけ (名前・書式は第 2 群で確認)
  host-shell bridge --forward-local 8080:localhost:3000 --forward-remote 15432:db.local:5432 -- ssh -T target host-shell --mcp ...
```

```text
案 B: MCP ツールだけ (bridge の起動オプションは許可範囲だけ)
  host-shell bridge --forward-allow ... -- ssh ...
  エージェント: forward_open {"direction": "local", "listen_port": 8080, "host": "localhost", "port": 3000}
```

```text
案 C: 両方
  起動オプションで定義した転送は接続直後に開始し、ツールでも許可範囲内で追加・削除できます。
```

### Q-041 受入条件

**Status**

解決済み

**Question**

次の受入条件でよいですか？

**Context**

第 1 群・第 2 群の回答 (第 3 群は推奨案) を前提とした受入条件の案です。時間に関わる検証 (無通信の維持、確立待ち 30 秒) は、時計やタイムアウト値を注入して短時間で行います。

1. ローカル転送・リモート転送・SOCKS5 (CONNECT、IPv4・IPv6・ドメイン名) で、バイナリ・大容量・双方向・片方向終了の往復を、ローカルの試験サーバーで確認します。
2. 常設転送 (ポート 0 の自動割当、`[::1]` を含む) と、forward_open・forward_close・forward_status (常設転送の close 拒否、close 時の既存接続の切断、公開条件) を確認します。
3. 要求と許可の照合を確認します。許可のない要求の起動エラー、許可だけでの正常起動、要求なしでの通常 MCP、HTTP プロキシの両端必須の維持、旧定義の相手の検出です。
4. 宛先の制限を確認します。接続先 `--allow-host` (ローカル転送・SOCKS)、bridge の規則 (ツール作成・SOCKS)、`--forward-socks` の規則必須、SOCKS の応答コード、診断履歴の理由・ページング・脱落です。
5. 待ち受けを確認します。ループバック以外の拒否、ポート使用中 (常設は起動エラー、ツールはエラー)、接続先でのリモート転送の待ち受け失敗です。
6. 上限を確認します。64 接続の共有と超過、16 転送と超過、ポート転送の無通信での維持と HTTP プロキシの 5 分の維持です。
7. 通信の安全性を確認します。双方向の open の採番が衝突しないこと、接続先が未登録の転送や任意の宛先への接続を bridge に開かせられないこと、不正フレーム、切断・キャンセル時の全資源の解放 (goroutine を含む) です。
8. 接続先の監査ログと sys_get_info の内容、および本文を記録しないことを確認します。
9. 既存 HTTP プロキシの全テスト、通常ツール・resources・ファイル転送が、各機能の有効・無効の組み合わせで維持されることを、インメモリと実 stdio 子プロセスの結合テストで確認します。
10. make、6 ターゲットのクロスビルド、全 OS の CI を確認します。未実施の検証は受入前に明示して扱いを確認します。
